1. `git ls-remote origin refs/heads/main` → 远端确实是 `90376ba`，说明**推送没问题**，问题在本地追踪引用。
2. `git fetch origin` **报告** `c8baf61..90376ba  main -> origin/main`，exit 0，但紧接着 `git rev-parse origin/main` 又是 `c8baf61`。
3. `git for-each-ref | grep origin` 只有 `refs/remotes/origin/main c8baf61`；`.git/refs/remotes/origin/` **目录不存在**；值来自 `.git/packed-refs`（**packed 里的旧值**）。
4. 关键实验：手工 `mkdir -p .git/refs/remotes/origin && printf '<sha>\n' > .git/refs/remotes/origin/main` → `rev-parse` 立刻正确，且**跨调用持久**。
5. 再跑一次 `git fetch origin` → 那个目录**又被删了**，值回落 packed-refs。
→ **定论：`git fetch` 会删除 `.git/refs/remotes/origin/` 整个目录**，于是永远回落到 packed-refs 里的陈旧值。（`git update-ref` 同样：返回 exit 0 但目录随后消失。）

**修法**：直接把 `.git/packed-refs` 里的追踪引用改对（sed 替换那一行）——
`sed -i 's|^<old_sha> refs/remotes/origin/main$|<new_sha> refs/remotes/origin/main|' .git/packed-refs`
之后即使 loose ref 再被 fetch 删掉，回落值也是对的。实测 fetch 后 `## main...origin/main` 不再显示 ahead。

**归因**：和记忆里那条「沙箱内 `git rm` 会连整个目录一起删（`backend/app/` + `backend/tests/`）」是**同一类毛病**——本沙箱的 git 内部删除逻辑不可靠。**推论：本仓库里凡是依赖 `.git/refs/` 的自动维护（fetch / update-ref / 可能的 gc/pack-refs）都不要盲信结果，改完 ref 后用 `git ls-remote` + `rev-parse` 双向核对。**

**另**：`type git` = `/mingw64/bin/git`（真 binary，未被包装；`rm` 才是被包装的 bash 函数）。

## 2026-09-11 夜：为什么会有 release-build / -build2 / -build3 一堆目录

**用户质问**："为什么搞那么多 release 文件夹，打包新的就删掉旧的呗" —— 他说得对，是我处理得糙。

**根因**：electron-builder 的输出目录（`directories.output`）里，`win-unpacked/resources/app.asar` 会被**泄漏的进程句柄**占住。一旦该目录被占，下一次构建到**同一目录**就会在删除旧 `app.asar` 时失败。我的应付方式是**每次换一个新目录名**（`release` → `release-build` → `release-build2` → `release-build3`），于是越堆越多。

**定位实验（结论明确）**，针对锁住的 `app.asar`：
- 新建一个**同名** `app.asar`（同路径模式）→ **能删** ⇒ 不是文件名/路径模式。
- 把它**复制**一份出来 → 副本**能删** ⇒ 不是内容。
- 同目录里**其他文件** → **能删** ⇒ 不是目录权限。
- 原地**重命名** → 失败（`Device or resource busy`）⇒ 是真·打开句柄（多半是 mmap 了 asar）。
- 四个目录的 app.asar **全被占**（连从没运行过的 `release-build3` 也是）⇒ 系统层面有人持有，`tasklist` 找不到、`Add-Type`（Restart Manager）被安全策略拦、自写 NtQuerySystemInformation 句柄枚举在本环境会**挂死**（`NtQueryObject` 卡住 / 进程太多）。
- **结论：本会话解不开，只能重启。** 用户已去重启。

**清理进展**：`rm -rf` 已把 `release/`、`release-build/` 清成"只剩一个锁住的 app.asar 的空壳"；`release-build2/`（含 Setup.exe）和 `release-build3/` 内容仍在。
**重启后应做**：
1. 删掉全部 `release/`、`release-build/`、`release-build2/`、`release-build3/`。
2. 输出目录**回到单一的默认名**（`release/`），别再换名字。
3. 在构建流程里加**构建前清理**（先删旧输出目录再 build），避免再次堆积。
4. 保留一个可用安装包即可 —— 目前最新可用的是 `release-build3/Open Holdem Manager-Setup.exe`（前后端都已是最新代码 + WAL 自愈）。
